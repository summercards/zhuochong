## 六、发现的问题（未修，登记在案）

### 6.1 `Jacket_Hem` / `Jacket_Hem_Line` 未蒙皮

两个网格（960 tri + 256 tri）**没有 skin 绑定**，挂在普通节点上。
后果：跑动/倒地时外套下摆不跟随身体。

三种 GLB 里都是这样，说明是上游 Blender 阶段就没绑，不是导出丢的。
影响：视觉瑕疵。修法：Blender 里补 `thigh`/`shin` 权重重导。

**在横版模板里的显性症状（实测）：** 这两件不跟骨骼动，所以永远停在静止位姿上，
侧视画面里看起来是**一片悬在胸口高度的蓝色圆盘**。模板运行时按"是否绑了
`skeleton`"这个可验证信号隐藏它们，并断言数量 == 2（`Fighter.UNSKINNED_MESH_COUNT`）；
`tools/verify_assets.py` 用同一条判据（GLB 里缺 `JOINTS_0` 的 primitive 数）也加了门禁。
判据跟着资产状态走 —— 下摆将来绑进骨架后会自动回来，不需要记得改代码。

### 6.2 Action 的 `category` 属性与清单分类已漂移

实测 68 个 Action 的 `category` 自定义属性分布：

| category 值 | 数量 | 清单里的对应家族 |
|---|---|---|
| 基础移动 | 13 | 基础移动 ✅ |
| 普通攻击 | 10 | 普通攻击 ✅ |
| 连招与特殊技 | 14 | 连招与特殊技 ✅ |
| **防御** | **4** | 应为「防御与受击」❌ |
| **防御与受击** | **15** | 「防御与受击」✅ |
| **状态与流程** | **8** | 应为「状态与流程」✅ |
| **状态与战斗流程** | **3** | 应为「状态与流程」❌ |

7 段动画的属性值跑到了另一套命名上（`防御` / `状态与战斗流程`），
`Death` / `Revive` / `Defeat` 三段用了"状态与战斗流程"这个只在早期存在过的名字。

**后果**：程序若按 `category` 分组会得到 7 个组而不是 5 个。

**处置**：`docs/动画文档.md` 与 `manifest.json` **一律以清单 A–E 家族为准**，
Action 属性值只作参考。要修的话得跑一遍 Blender 重写 Action 属性，成本不高但不急。

### 6.3 `Charge_Loop` 不占清单行

清单是 67 行，Blend/GLB 是 68 段。多出的是 `Charge_Loop`（36 帧），
是 `C08 Charge` 的配套循环段，在 C08 的制作日志里登记过，只是没单独占一行。

**这不是缺漏**，两套口径都自洽。但程序侧遍历 clips 时要注意总数是 68 不是 67。

### 6.4 `Guard_Loop` 在引擎里被改名为 `Guard`

**这也不只是"问题"，而是一条必须显式管理的跨层契约。**

Godot 的 glTF 导入器会把动画名结尾的 `_Loop` 当循环标记去掉 —— 但**仅当去掉后不撞名**。
本资产因此产生 1 条清单名 ≠ 引擎名：

| 清单名（语义权威） | 引擎名（Godot 内） |
|---|---|
| `Guard_Loop` | `Guard` |
| `Charge_Loop` | `Charge_Loop`（去掉会撞 `Charge`，故未改） |

对照实验证明触发条件是"`_Loop` 后缀 + 无撞名"：把 `Guard_Loop` 等长改名为
`GuardXLoop` 后，Godot 原样保留。

**三处盯着这条契约**：`animations/engine_names.json`（数据）、
`Fighter._apply_loop_modes()`（运行时断言）、`tools/verify_assets.py`（门禁重算比对）。
详见 `docs/动画文档.md` 第 10.4 / 10.5 节。
